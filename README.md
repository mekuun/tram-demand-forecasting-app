# Описание собранных данных

## Запуск сервиса через Docker

В проекте есть два контейнера: `backend` на FastAPI и `frontend` на Next/Vinext. Backend читает готовый CSV `frontend/ui_forecasts.csv`, календарь событий и возвращает фронтенду сводку, heatmap, прогнозы по маршрутам и CSV-экспорт. Обучение и инференс находятся в отдельном репозитории и здесь не запускаются.

```bash
docker compose up --build
```

После запуска:

- интерфейс: http://localhost:3000;
- API: http://localhost:8000;
- Swagger: http://localhost:8000/docs;
- проверка backend: http://localhost:8000/health.

Основной запрос интерфейса:

```text
GET /api/v1/dashboard?date=2025-12-31&route_id=17&hour=18
```

Адрес API для фронтенда задаётся переменной `NEXT_PUBLIC_API_URL`. Для локальной разработки без Docker можно запустить backend командой `uvicorn backend.app.main:app --reload --port 8000`, а frontend — из папки `frontend` командой `npm run dev`.

Путь к готовому CSV можно переопределить переменной `FORECAST_CSV_PATH`. Для Docker файл подключён как `/app/frontend/ui_forecasts.csv`; чтобы обновить прогноз, достаточно заменить CSV и пересобрать frontend/backend.

Набор данных подготовлен для исторического прогноза пассажиропотока трамваев Москвы.

В эксперименте используются исторические наблюдения за январь–октябрь 2025 года, а пассажиропоток ноября–декабря 2025 года рассматривается как прогнозный период. Календарь мероприятий используется как внешний фактор: модель получает информацию о датах, площадках, маршрутах и времени событий, но не получает фактическую посещаемость мероприятий или фактические пики пассажиропотока.

## Основной календарь: `events_2025.csv`

Каждая строка соответствует мероприятию или событийной программе. Для многодневных мероприятий интервал задаётся полями `date_start` и `date_end`.

### Поля

| Поле | Описание |
|---|---|
| `event_id` | Уникальный идентификатор события |
| `date_start` | Дата начала события |
| `date_end` | Дата окончания события |
| `start_time_local` | Время начала активной программы в московском времени |
| `end_time_local` | Время окончания активной программы |
| `end_day_offset` | Переход через полночь: `0` — в тот же день, `1` — окончание на следующий день |
| `duration_hours` | Продолжительность программы в течение одного дня |
| `session_schedule_local` | Времена отдельных сеансов через разделитель `|` |
| `time_profile` | Тип распределения спроса по времени |
| `temporal_concentration_coefficient` | Коэффициент концентрации пассажиропотока по времени |
| `time_quality` | Качество временной оценки |
| `event_name` | Название события |
| `event_type` | Тип события: концерт, фестиваль, ярмарка, спортивное событие и т. п. |
| `venue_id` | Идентификатор площадки или городской программы |
| `venue_name` | Название площадки |
| `nearby_tram_routes` | Ближайшие трамвайные маршруты |
| `impact_class` | Класс воздействия события |
| `source_quality` | Качество источника |
| `source_url` | Ссылка на источник |
| `popularity_coefficient` | Стандартизированный коэффициент общего масштаба аудитории |
| `affected_branches` | Затронутые маршруты; для общегородских программ используется `ALL_CITY` |

Маршруты в поле `nearby_tram_routes` разделены символом `|`. Например:

~~~
11|17|25
~~~

Это означает, что событие связано с маршрутами 11, 17 и 25.

## Таблица связей: `event_route_effects_2025.csv`

Эта таблица предназначена для непосредственного объединения с пассажиропотоком. В ней одна строка соответствует одной связи:

~~~
событие × маршрут
~~~

Например, одно событие ВДНХ будет представлено тремя строками — для маршрутов 11, 17 и 25.

В таблице сохранены:

- дата и временное окно;
- затронутый маршрут;
- коэффициент популярности;
- коэффициент временной концентрации;
- профиль события;
- длительность;
- расписание сеансов;
- тип и класс воздействия.

Для строк с `route_id=ALL_CITY` событие не привязано к конкретной трамвайной ветке. Такие события следует использовать как отдельный общегородской фактор или распределять по маршрутам через дополнительные веса.

## Шкала популярности

`popularity_coefficient` измеряет не пассажиропоток за час, а потенциальный общий масштаб аудитории события относительно крупнейших событий в наборе.

| Диапазон | Интерпретация |
|---:|---|
| `0.00–0.29` | малое событие |
| `0.30–0.49` | локальная или умеренная программа |
| `0.50–0.69` | крупная распределённая программа |
| `0.70–0.84` | крупное площадочное событие |
| `0.85–1.00` | крупнейшее городское или массовое событие |

Важно: одинаковый коэффициент популярности не означает одинаковый почасовой профиль.

Например, парк, каток или ярмарка могут привлечь столько же людей за день, сколько концерт, но посетители будут приходить равномерно в течение нескольких часов. Поэтому для них используется более низкий коэффициент временной концентрации.

## Коэффициент временной концентрации

`temporal_concentration_coefficient` описывает, насколько сильно поток сосредоточен около начала и окончания события.

| Диапазон | Тип профиля |
|---:|---|
| `0.00–0.29` | равномерный дневной поток |
| `0.30–0.49` | смешанный или распределённый поток |
| `0.50–0.69` | заметная концентрация вокруг программы |
| `0.70–0.84` | сильная концентрация вокруг сеансов |
| `0.85–1.00` | резкий пик до начала и после окончания |

Примеры:

- каток ВДНХ: высокая общая популярность, но низкая концентрация;
- концерт: высокая популярность и сильный вечерний пик;
- детская ёлка: несколько отдельных пиков по расписанию сеансов;
- новогодняя ночь: высокий коэффициент концентрации и переход через полночь.

## Временные профили

Поле `time_profile` используется для построения почасового сигнала:

| Профиль | Пример |
|---|---|
| `concert_peak` | концерт с пиком до начала и после окончания |
| `stadium_peak` | крупное стадионное событие |
| `match_peak` | спортивный матч |
| `multi_session` | детские спектакли и ёлки с несколькими сеансами |
| `distributed_citywide` | городская программа, ярмарки, сезонные фестивали |
| `distributed_venue` | каток или длительная программа на одной площадке |
| `festival_evening` | фестиваль с вечерним усилением |
| `new_year_peak` | программа, переходящая через полночь |

Для базовой модели почасовой эффект события можно рассчитывать как:

~~~
event_effect =
    popularity_coefficient
    × temporal_concentration_coefficient
    × hourly_time_profile
~~~

`hourly_time_profile` должен учитывать:

- подготовительный период до начала;
- основной интервал события;
- выход посетителей после окончания;
- отдельные пики для `session_schedule_local`;
- переход на следующий день при `end_day_offset=1`.

## Пример расчёта

Для концерта:

~~~
popularity_coefficient = 0.70
temporal_concentration_coefficient = 0.85
start_time = 19:00
end_time = 22:00
~~~

Ожидаемый профиль:

- умеренный рост примерно с 17:00;
- основной пик около 18:00–19:00;
- дополнительный пик после 22:00.

Для катка:

~~~
popularity_coefficient = 0.65
temporal_concentration_coefficient = 0.25
start_time = 10:00
end_time = 22:00
~~~

Ожидаемый профиль — более ровный поток в течение дня без резкого единственного пика.

## Ограничения

1. Коэффициенты популярности являются экспертными априорными оценками, а не измеренной посещаемостью.
2. Для части мероприятий точные часы начала и окончания не были опубликованы в исходном календаре. Такие строки имеют `time_quality=estimated_window` или `partial_known`.
3. Для общегородских событий пока нет точного распределения посетителей по маршрутам.
4. Многодневные фестивали не должны давать одинаковый резкий пик каждый день: если доступна детальная программа, её нужно развернуть в отдельные дневные события.
5. Для строгого исторического backtest необходимо дополнительно фиксировать, была ли информация о событии опубликована до даты формирования прогноза. Фактическая посещаемость и фактические транспортные пики в эти файлы не добавлялись.
